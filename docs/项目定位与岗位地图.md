# 项目定位与岗位地图

> 这份文档解决两个问题：**这个项目在面试官眼里到底是什么？** 以及 **它把你送到哪些岗位门口？**
> 写简历、准备面试话术时直接对照本文，不要临场编。

---

## 一、项目定位：三层，一层都不能吹

### 层 1：它是"理解工具"，不是"产品"

| | 你的项目 | 观测云 DataKit |
|---|---|---|
| 代码量 | 目标 1500–2500 行 Go | 约 2000 万字节 Go |
| 采集器数量 | 3–4 个 | 650+ |
| 用户 | 你 | 1000+ 企业 |

**所以正确的说法是：**

> 我读了 DataKit 的插件注册机制和 Point 数据模型，然后用 2000 行 Go 复刻了核心链路，用来验证我对它的理解。

**错误的说法是：**

> 我写了一个类似 DataKit 的采集器。

后一种说法会招来"那你处理过 650 种采集器的配置兼容吗""Pipeline 语法你怎么做的"——**当场被问穿**。

诚实划边界的人反而可信。主动说"我只做到这里"，比被问出来强一百倍。

### 层 2：它的价值在"每一层都能讲出取舍"

面试官不会问"你写了多少行"，只会问"为什么这么设计"。这个项目给了你 **6 个可以讲满 3 分钟的取舍点**：

| # | 设计点 | 对应的真实面试题 |
|---|---|---|
| 1 | 插件注册表（`init()` + 下划线导入）而不是 switch-case | "新增一种采集器要改几个文件？为什么？" |
| 2 | `Point` 用 map 而不是固定 struct | "schema-free 和类型安全你怎么取舍？" |
| 3 | counter 必须存上一次采样值 | "Prometheus 的 counter 和 gauge 有什么区别？rate 怎么算？" |
| 4 | 批量上报 + 背压 | "采集端把服务端打挂了怎么办？" |
| 5 | 按时间分片 + 二分剪枝 | "时序数据为什么适合按时间分片？" |
| 6 | 一键验证脚本 | "你怎么判断 AI 写的代码是对的？" |

**这 6 个点就是项目的真正产出。** 不是那 2000 行代码，是这 6 段能讲的话。

### 层 3：它证明的是"工程闭环"，不是"领域深度"

要分清两件事：

- **领域知识**（eBPF、Platypus Pipeline 语法、GuanceDB 存算分离）——你只能讲到"我知道它存在、解决什么问题"，讲不到"我实现过"。**不要假装。**
- **工程闭环**（从 0 到能跑、有测试、有文档、有验证脚本、能演示）——你是真做过，可以讲细节。

面试时主动划这条线：

> eBPF 采集我只读过文档，没动手做过；但我自己实现的这条链路，从采集到查询每一层的取舍我都能讲。

这句话的杀伤力远大于硬撑。

## 二、你实际获得的能力

按"能在面试里讲多深"排序，不是按知识点多少：

| 能力 | 深度 | 证据 |
|---|---|---|
| Go 工程能力（接口、并发、测试、错误处理） | 能写能改 | 2000 行代码 + 单测 |
| 插件化 / 开闭原则的落地 | 能讲清 | `registry.go` |
| 时序数据建模（counter/gauge、tag/field） | 能讲清 | `point.go` + `cpu.go` |
| 并发与背压 | 能讲清 | W2 的采集池 |
| 存储与索引（分片、二分） | 能讲清 | W4 |
| 查询与聚合 | 能跑能讲 | W5 |
| 性能分析（pprof、火焰图） | 亲手做过一次 | W6 |
| Linux 系统（/proc、文件描述符） | 摸过 | W1–W3 |
| 容器化与部署 | 会用 | W9 |
| **AI 辅助开发的流程化**（AGENTS.md / Skills / 验证脚本） | **能讲清且有物证** | W8 |

最后一项是**稀缺项**。2026 年会写 Go 的应届生很多，能拿出"我用 AI 干活，而且有流程和验证体系"物证的很少。

## 三、岗位地图：能投什么、匹配度多少

### ★★★★★ 第一梯队：直接对口

| 岗位 | 典型公司 | 你需要额外补什么 |
|---|---|---|
| 可观测性研发 | 观测云、Datadog、阿里云 ARMS、夜莺 n9e、OneAPM、蓝鲸 | OpenTelemetry / OTLP、Prometheus 数据模型 |
| 监控 / APM 平台开发 | 各类 SaaS 与中大厂基础架构部 | 同上 + 一点 Kubernetes |
| 采集 Agent 开发 | Telegraf、Vector、Fluent Bit、OTel Collector 生态 | 插件生态设计、配置兼容 |

**这是你命中率最高的方向。** 你的项目就是这条链路的最小实现。

### ★★★★ 第二梯队：强相关

| 岗位 | 典型公司 | 额外要补 |
|---|---|---|
| 时序数据库 / 存储引擎 | TDengine、GreptimeDB、VictoriaMetrics、InfluxDB | LSM tree、列存、压缩编码（Gorilla / delta-of-delta） |
| AI Coding 工程化 / AI 应用工程 | 各类"AI 原生"团队（含观测云本岗） | MCP、Agent 编排、评测（eval） |
| DevOps / SRE / 平台工程 | 大部分互联网公司 | CI/CD、K8s、Linux 运维 |

### ★★★ 第三梯队：可以投，但项目只撑到初级

| 岗位 | 说明 |
|---|---|
| Go 后端开发 | 项目能证明 Go 能力，但缺 MySQL/Redis/分布式这些"后端基本功" |
| 基础架构 / 中间件 | 同上，且竞争激烈 |

### 不匹配（不要浪费时间）

- **算法 / 模型训练 / 数据科学**：你的项目是工程向，跟模型无关。
- **前端 / 客户端**：无关。
- **"AI 大模型应用"里偏 prompt 调优的岗**：除非你补 RAG/Agent 实战，单靠这个项目撑不住。

## 四、一个必须提前准备的坑

你是**人工智能专业**，简历上却是"一个监控采集项目"。面试官一定会问：

> 你学 AI 的，为什么做这个？为什么不做 AI？

**准备一个 30 秒的答案，核心是"我选择做让 AI 参与工程，而不是做模型本身"：**

> 我的专业让我清楚模型能做什么、不能做什么——它能写代码，但它不知道自己写对没有。所以我把方向定在"怎么让 AI 稳定地参与工程"，具体就是给项目写 AGENTS.md、把常用操作固化成 Skill、用一条命令跑完格式/静态检查/并发测试。这个项目里的 AI 协作流程，就是我给这个问题的答案。

这个答案比"我也想做大模型但是..."强得多，而且**和观测云这个岗位的 JD 完全对得上**（它要的就是"沉淀 Prompt / Skills / 脚本 / 验证流程"）。

## 五、三个版本的电梯陈述

不同岗位投不同版本，30 秒说完，别啰嗦。

### 投可观测性（观测云、ARMS、夜莺）

> 我读了观测云 DataKit 的插件机制，用 Go 写了约 2000 行的最小采集端，覆盖采集、批量上报、时序存储、类 DQL 查询四层，采集到的数据能打进观测云控制台。每一层的设计取舍我都能讲清为什么。

### 投 Go 后端

> 我用 Go 从零写了一个采集 Agent 加服务端：Agent 侧做插件化采集和批量上报，服务端侧做时间分片存储和范围查询。重点解决了两个问题——上报把服务端打挂时的背压，以及数据量涨上来之后的查询剪枝。

### 投 AI 工程化（含观测云本岗）

> 我给自己的项目建了一套 AI 协作流程：AGENTS.md 定规矩、两个 Skill 固化常用操作、一个脚本跑完格式检查/静态检查/并发测试。让 AI 改代码这件事从"靠感觉"变成"有验收标准"。

## 六、简历上的三行怎么写（W9 再填数字）

结构固定：**做了什么 → 难点是什么 → 结果是多少**。第三行必须有数字。

```
mini-datakit｜个人项目｜Go
· 从零实现插件化采集 Agent + 服务端，覆盖采集、批传、时序存储、查询四层，
  零第三方依赖，XX 个单测全绿
· 解决批量上报的背压问题：队列满时丢弃低优先级采集项而非阻塞，P99 上报延迟从 XX 降到 XX
· 时间分片 + 二分剪枝，XX 万点数据下范围查询从 XX ms 降到 XX ms（附 pprof 火焰图）
```

**没有数字的项目描述等于没写。** W6 的 pprof 优化就是专门用来产出这行数字的，别偷懒不做。

## 七、名字的事（W9 再处理）

**现在别改**——改名要动 `go.mod` 和所有 import，等 W9 打包时一次搞定。
